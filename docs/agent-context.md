# AI 에이전트가 먼저 읽을 문서

이 문서는 신석진이라는 사람의 이력서를 다룰 때, AI 에이전트가 무엇을 중심에 두고 읽고 써야 하는지 정리한 기준입니다. 단순히 프로젝트를 나열하기보다, 어떤 문제를 오래 보고 어떤 방식으로 일하는지를 빠르게 파악하기 위한 문서입니다.

## 한 문장으로 보면

사용자 흐름에서 시작해 운영자 판단, 데이터 정합성, 앱과 웹의 경계, 배포와 품질 기준까지 함께 보는 프론트엔드 엔지니어입니다.

## 일을 볼 때의 기본 관점

- 화면은 단독으로 완성되지 않습니다. 사용자의 행동, 운영자의 판단, 서버 응답, 데이터 상태, 배포 환경이 함께 맞아야 제품 경험이 안정됩니다.
- 빠르게 만드는 것보다 다시 틀리지 않게 만드는 일을 중요하게 봅니다. 반복되는 테이블, 폼, 권한, 라우팅, 배포 흐름은 공통 기준으로 줄이되, 제품마다 달라야 하는 책임은 남깁니다.
- 앱과 웹, 사용자와 관리자, 화면과 데이터처럼 책임이 흐려지는 경계를 오래 봅니다. 문제가 어느 계층에서 생겼는지 나누어야 재현과 수정이 빨라진다고 봅니다.
- 테스트와 리뷰는 형식이 아니라 기억을 줄이는 장치입니다. 사람이 나중에 읽고 판단할 수 있도록 변경 단위와 시나리오를 작고 분명하게 남기려 합니다.

## 반복해서 드러나는 경험 축

- 글로벌 사용자 웹: 커뮤니티, 포인트, 구매 전환, 리뷰, 다국가 언어 상태, 캐시, 이미지 응답 속도
- 앱 웹뷰: Flutter 앱과 React/Next.js 웹뷰 사이의 토큰 전달, 딥링크, 안전 영역, iOS 키보드, 실기기 재진입 문제
- 운영 관리자: 공지, 이벤트, 고객, 포인트, 콘텐츠 검토, 배송, 승인 상태를 운영자가 잘못 판단하지 않도록 만드는 화면
- 크리에이터 운영: 캠페인, SNS 연동, 콘텐츠 리뷰, VoC, 제품 발송, 주소·관세·계좌 예외를 상태와 알림으로 정리한 경험
- 데이터와 로그: 공개 채널 랭킹·리뷰 모니터링, 사용자 행동 로그, 캠페인 유입 맥락, 대시보드 성능
- 배포와 품질: GitHub Actions, Jenkins, EKS/ECS, 보안·정적 분석, 실패 알림, 관측성, 롤백 가능성
- 초기 제품 출시: EVPAY에서 사용자 앱과 관리자 도구를 함께 만들며 출시와 운영 기반을 잡은 경험
- 개인 작업: WebSocket/WebRTC 직접 구현, 상태 관리와 데이터 접근 도구 실험, 오픈소스 패키지 설계

## 글을 쓸 때 지켜야 할 것

- 실제 회사 경험은 숨기지 않습니다. 에이피알, EVAR, 메디큐브프로, 포토그레이, EVPAY처럼 본인의 실제 이력과 제품 경험은 이력서의 핵심 근거입니다.
- 특정 외부 조직에 맞춘 해석, 동기 문장, 맞춤 분석은 공개 문서와 배포물에 넣지 않습니다.
- 공개 범위 밖의 조직·저장소·변경 이력·코드 식별자는 공개 문서에 쓰지 않습니다.
- 기능 목록만 나열하지 않습니다. `문제 상황 -> 맡은 책임 -> 만든 구조 -> 운영이나 사용자에게 남은 변화` 순서로 정리합니다.
- 추상어만 반복하지 않습니다. `구조`, `흐름`, `기준`, `연결` 같은 단어를 쓸 때는 반드시 실제 화면, 업무, 데이터, 배포 조건 중 하나와 붙여 씁니다.
- 과장하지 않습니다. 수치가 있으면 근거가 있는 범위에서만 쓰고, 소유권이 애매한 일은 팀 맥락과 본인이 맡은 책임을 나누어 표현합니다.

## 문서 사용법

- 웹 배포판의 현재 원본은 `src/resume.content.ts`입니다.
- 공개 보조 문서의 목차는 `docs/index.md`입니다.
- 내부 근거와 작업 메모는 공개 저장소에 커밋하지 않습니다.
- 공개 문서를 수정할 때는 먼저 특정 외부 조직 맥락이나 공개 범위 밖의 식별자가 섞이지 않았는지 검색합니다.
