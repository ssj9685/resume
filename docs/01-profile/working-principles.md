# 함께 일할 때 지키려는 기준

저는 일을 잘한다는 말을 빠르게 많이 만드는 것만으로 이해하지 않습니다. 함께 일하는 사람이 덜 헷갈리고, 운영자가 덜 실수하고, 다음에 같은 문제가 생겼을 때 더 빨리 알아차릴 수 있어야 좋은 일이라고 생각합니다.

## 사용자 경험과 개발자 경험은 이어져 있다

사용자에게는 빠른 반응과 안정적인 흐름이 중요합니다. 하지만 그 경험은 만드는 사람의 경험과도 연결되어 있습니다. 코드가 읽히지 않고, 같은 구조를 매번 다시 만들고, 테스트가 맥락을 설명하지 못하면 결국 사용자에게도 불안정한 화면이 전달됩니다.

그래서 저는 사용자 경험과 개발자 경험을 따로 보지 않습니다. 사용자가 덜 기다리게 만드는 일과 개발자가 덜 헤매게 만드는 일은 같은 방향을 향한다고 생각합니다.

## 문제는 한 계층에 갇혀 있지 않다

화면에서 보이는 문제의 원인이 화면 안에만 있는 경우는 많지 않았습니다. 데이터가 늦게 오거나, 연동 규약이 애매하거나, 배포 환경이 흔들리거나, 운영자가 기대한 상태와 화면이 다를 수 있었습니다.

그래서 문제를 볼 때는 화면, 서버, 데이터, 배포, 운영 흐름을 나누어 봅니다. 한 계층만 고치면 증상이 사라지는 것처럼 보여도, 실제 원인이 다른 곳에 남아 있으면 같은 문제가 다시 돌아온다고 생각합니다.

## 요구사항이 완성되기를 기다리지만은 않는다

일정이 촉박하거나 요구사항이 완전히 정리되지 않은 상황에서는 먼저 기준안을 만들 필요가 있습니다. 완성된 기획서를 기다리기보다 핵심 흐름을 잡고, 개발 과정에서 기획과 사용자 경험을 함께 보완하는 방식을 자주 택했습니다.

이때 중요한 것은 속도만이 아닙니다. 어디까지 확정된 것인지, 어떤 예외를 나중에 다시 봐야 하는지, 어떤 결정이 운영 리스크로 이어질 수 있는지를 함께 남겨야 합니다.

## 공통화는 모든 것을 묶는 일이 아니다

반복되는 테이블, 폼, 권한, 라우팅은 팀의 속도를 늦춥니다. 하지만 공통화가 모든 차이를 지워도 안 됩니다. 반복되는 책임은 모으고, 서비스마다 달라야 하는 책임은 남겨야 오래갑니다.

제가 만들고 싶은 공통 구조는 개발자가 덜 타이핑하는 구조가 아니라, 팀이 같은 기준으로 읽고 고칠 수 있는 구조입니다.

## 리뷰와 테스트는 기억을 줄이는 장치다

코드 리뷰는 승인 절차라기보다 흐름과 책임을 함께 확인하는 시간에 가깝습니다. 조건 분기가 어색한지, 상태 전이가 분명한지, 사용자와 운영자의 실제 흐름이 코드에 반영되어 있는지를 봅니다.

테스트도 실패를 잡는 도구에만 머물면 아쉽습니다. 좋은 테스트는 나중에 읽었을 때 왜 이 기능이 이렇게 동작해야 하는지 설명하는 문서가 됩니다. 특히 자동화 도구가 코드를 더 빨리 만드는 환경에서는, 사람이 검토할 수 있는 단위와 시나리오가 더 중요해진다고 생각합니다.

## 배포와 운영도 제품의 일부다

프론트엔드 품질은 코드와 화면만으로 결정되지 않습니다. 빌드가 안정적으로 되고, 실패했을 때 되돌릴 수 있으며, 문제가 생겼을 때 원인을 추적할 수 있어야 합니다.

그래서 배포와 관측, 실패 알림, 롤백 가능성까지 제품 경험의 일부로 봅니다. 좋은 화면도 안정적으로 전달되지 않으면 제품으로 완성됐다고 보기 어렵습니다.
