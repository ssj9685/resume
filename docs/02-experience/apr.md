# APR에서의 나

APR은 제가 프론트엔드를 화면 구현의 영역으로만 보지 않게 만든 환경입니다. 사용자 서비스, 웹뷰, 관리자, 정산, 물류, 데이터, 배포가 서로 연결되어 있었고, 한쪽의 작은 결정이 다른 쪽의 운영 부담으로 이어지는 장면을 많이 봤습니다.

## 화면에서 시작한 경험

처음에는 리액트와 넥스트 기반 사용자 서비스와 관리자 화면을 많이 다뤘습니다. 포인트, 보상, 구매, 이벤트, 사용자 콘텐츠, 앱테크처럼 사용자의 행동이 바로 운영과 데이터 정합성으로 이어지는 기능이 많았습니다.

이때 배운 것은 사용자가 보는 화면이 실제로는 여러 조직의 업무와 연결되어 있다는 점입니다. 버튼 하나, 필터 하나, 상태값 하나가 운영자의 판단과 고객 응대에 영향을 줄 수 있었습니다.

## 웹뷰에서 배운 경계

플러터 앱 안에서 동작하는 웹뷰를 다루며 브라우저와 실기기의 차이를 많이 경험했습니다. 메모리 누수, 캐시 불일치, 서버 렌더링 중 번역이 흔들리는 문제, 안전 영역, 키보드, 딥링크 같은 문제는 프론트엔드 코드만 봐서는 충분하지 않았습니다.

이 경험은 제가 문제를 한 계층에 가두지 않는 습관을 갖게 했습니다. 앱, 웹, 연동 규약, 배포, 실제 단말 상태를 같이 봐야 원인이 좁혀졌습니다.

## 관리자와 운영 도구의 책임

관리자 화면은 내부 도구처럼 보이지만 실제로는 운영자가 실수를 줄이고 빠르게 판단하기 위한 제품입니다. 공지, 이벤트, 고객, 포인트, 승인, 정산, 물류가 연결되어 있었고, 화면 구조가 곧 업무 구조가 되는 경우가 많았습니다.

그래서 관리자 화면을 만들 때는 입력과 저장이 되는지뿐 아니라, 사람이 잘못 판단하지 않도록 돕는 구조인지 함께 보게 됐습니다.

## 리드 역할과 기준 정리

파트장 역할을 맡으며 모든 문제를 직접 해결하는 것보다 팀이 같은 기준으로 판단할 수 있게 만드는 일이 중요하다는 것을 배웠습니다. 코드 리뷰, 테스트, 공통 구조, 배포 기준은 모두 팀이 같은 문제를 덜 반복하기 위한 장치였습니다.

AI 도구를 쓰는 흐름도 이 관점에서 봤습니다. 코드를 빨리 만드는 것보다 사람이 검토할 수 있는 단위로 나누고, 테스트가 시나리오처럼 읽히도록 만드는 것이 더 중요했습니다.

## 지금의 기준

APR을 거치며 가장 분명해진 것은 연결해서 보는 습관입니다. 사용자 행동, 운영 절차, 연동 규약, 데이터, 배포 환경은 따로 떨어져 있지 않았습니다.

지금도 문제를 볼 때는 화면에서 보이는 증상, 운영자가 판단하는 기준, 데이터와 배포 조건, 재발을 더 빨리 알아차릴 방법을 함께 확인하려고 합니다.
